Architecture

Internet | v OpenShift Route | v Frontend Service | v Frontend Pod (Nginx) | v Backend Service | v Backend Pod(s) (Flask + Gunicorn) | v MySQL Service | v MySQL Pod | v PersistentVolumeClaim (mysql-data)

Only the frontend is directly accessible from the Internet through an OpenShift Route. The backend and MySQL database use internal ClusterIP Services and are not directly exposed to the Internet.

1. End-to-End Functionality

The frontend communicates with the backend using the Kubernetes backend Service. The backend then communicates with MySQL using the mysql Service.

The database interaction includes both a read and a write. The backend increments the persistent visit counter and executes SELECT NOW() to retrieve the current MySQL server time.

2. Configuration and Secrets

Application configuration is not hard-coded into the container images. Kubernetes ConfigMaps and Secrets are used to provide configuration to the containers.

A ConfigMap stores non-sensitive configuration such as the database host, database name and database user. A Secret is used for sensitive values such as database passwords.

The real Secret manifest is excluded from the Git repository using .gitignore. The repository only contains 01-secret.example.yaml with placeholder values.

3. Persistent Database Storage

MySQL uses a Kubernetes PersistentVolumeClaim called mysql-data. The database files are therefore stored independently of the lifecycle of an individual MySQL Pod.

Persistence experiment

I first loaded the application and recorded the current value of the visit counter. I then manually deleted the MySQL Pod. The MySQL Deployment created a new Pod and mounted the same persistent storage. After the new Pod became ready, I reloaded the application.

The counter continued from its previous value instead of returning to zero. This verified that the database data survived replacement of the MySQL Pod.

Comparison with Docker Compose

In the previous Docker Compose deployment, MySQL persistence was provided by a Docker named volume. I also tested this locally by recreating the database container and checking that the visit counter remained stored.

Both solutions separate persistent data from the container itself. The main difference is that Docker Compose manages the named volume on the Docker host, while Rahti uses a PersistentVolumeClaim managed by Kubernetes/OpenShift and the cluster storage system.

4. Pod Recovery

To test self-healing, I manually deleted the running backend Pod. The backend Deployment had a desired replica count of one.

After the Pod was deleted, the Deployment and its ReplicaSet detected that the actual state no longer matched the desired state. A new backend Pod was automatically created without manually starting a new container.

5. Backend Scaling

The backend Deployment was scaled from one replica to multiple replicas. I initially tried three replicas, but the third Pod could not be created because the CSC project CPU quota had been reached.

I therefore used two backend replicas, which was enough to verify the scaling behaviour. Both Pods were available behind the same Kubernetes backend Service.

The frontend does not need to know the IP addresses of individual backend Pods. It always communicates with the Service using backend:8000. Kubernetes handles communication with the available backend Pods.

After completing the experiment, the backend was returned to one replica.

6. Application Update and Rolling Deployment

To test application updates, I created a new frontend image and changed the application version from 1.0.0 to 1.0.1.

The frontend Deployment was updated to use the new image. During the rollout, OpenShift created a new frontend Pod and then terminated the old Pod. The rollout completed successfully.

Version 1.0.2 contains the final assignment documentation shown on this page. The 1.0.0 → 1.0.1 rollout above was the experiment used to verify the update behaviour.

7. Problems Encountered and Solutions

ARM64 and AMD64 container images

The first application images were built on an Apple Silicon Mac. They were ARM64 images, while the Rahti worker node required an AMD64 image. This caused the application Pods to fail with an ImagePullBackOff.

I solved the problem by rebuilding and pushing the frontend and backend images with Docker Buildx using --platform linux/amd64.

Nginx permissions

During the local container setup, Nginx initially had a permissions problem related to its PID file. I changed the frontend to use the unprivileged Nginx image and configured Nginx to run on port 8080.

CSC CPU quota

When I attempted to scale the backend to three replicas, OpenShift reported a FailedCreate event because the CSC project CPU quota was already reached. I reduced the test to two replicas, which successfully demonstrated horizontal scaling while staying within the available quota.

8. Docker Compose + cPouta vs Rahti

Area Docker Compose + cPouta Rahti
Deployment Containers are defined in one Compose file and run on a Docker host/VM. The application uses separate Kubernetes/OpenShift resources such as Deployments, Services, ConfigMaps, Secrets, Routes and PVCs.
Networking Containers communicate using Docker Compose service names and ports can be mapped directly from the host. Pods communicate through Kubernetes Services. Only the frontend is externally exposed through an OpenShift Route.
Persistence MySQL data is stored in a Docker named volume associated with the Docker host. MySQL uses a PersistentVolumeClaim that exists independently of an individual Pod.
Recovery Container lifecycle is mainly managed through Docker Compose and the Docker host. Deployments continuously maintain the desired number of Pods and automatically replace failed or deleted Pods.
Scaling Scaling can be performed with Compose, but the application still depends on the single Docker host unless additional infrastructure is introduced. Deployment replicas can be changed declaratively and Services provide a stable endpoint for multiple Pods.
Updates New container versions normally require recreating or updating containers on the Docker host. Deployments support controlled rolling updates between application image versions.

Docker Compose was simpler for running the three containers on one VM, while Rahti required more configuration. However, Rahti provided orchestration features such as self-healing, stable Services, scaling, persistent cluster storage and rolling deployments.

Week 5 - Public API Integration

For Week 5, I extended the three-tier application from Week 4 by integrating an external public API. The Flask backend now retrieves current weather information for Oulu from the Open-Meteo API.

A new /api/weather endpoint was added to the backend. The backend requests the external weather data and returns the relevant values to the frontend as JSON. The browser therefore communicates with my Flask backend instead of accessing the external API directly.

The extended data flow is: Frontend → Flask backend → Open-Meteo API. The original Frontend → Backend → MySQL flow is still used for the persistent visit counter and database time.

The integration displays the current temperature, apparent temperature, wind speed, weather condition and observation time. Open-Meteo was selected because it provides weather data through a REST API without requiring an API key for this use case.

Local test

I first tested the extended application locally using Docker Compose. The existing MySQL functionality and the new weather integration worked together correctly.

Deployment on CSC Rahti

After the local test, I built the updated container images and deployed the frontend and backend to CSC Rahti. The existing MySQL deployment and persistent storage were kept in the application architecture.

Testing the public endpoint

I verified the new endpoint through the public Rahti Route. A request to /api/weather returned JSON containing current weather information for Oulu, confirming that the deployed backend could communicate with the external Open-Meteo API.

Final result

Finally, I verified the integration from the deployed web application. The frontend receives the weather information from the Flask backend and displays it together with the original MySQL functionality.
